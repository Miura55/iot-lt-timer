# U1 拡張・容量要件

入力: [U1機能仕様](../functional-design/functional-spec.md)、[U1ルール](../functional-design/rules.md)、[requirements.md](../../../inception/requirements-analysis/requirements.md)、[unit-of-work.md](../../../inception/units-generation/unit-of-work.md)、[contract-summary.md](../../../inception/contract-design/contract-summary.md)。

| ID | 要件 | 設計・検証 |
|---|---|---|
| 容量プロファイル | 初版の機能範囲は1会場、ベル1台、同時進行1セッション、セッション当たり0〜10通知、1〜10800秒。 | 入力検証、会場の同時開始競合、最大通知数を過剰な負荷を作らず試験する。これは新たなNFRではなくFR1–FR4の容量境界。 |
| 利用者プロファイル | 少人数の許可済み主催者が同一状態を共有する。利用者数を無制限・公開登録として設計しない。 | 並行する複数主催者の状態取得・二重開始を試し、開始は1件のみ成功する。運用者数上限は認証選定時に設定可能とする。 |
| 実行環境 | バックエンド処理と保存データはstateless実行環境から共有でき、個別プロセスのメモリだけを時間・重複排除の正本にしない。 | 実行インスタンスを変えた読取・再開・古い起床試験を行う。NFR2.1–NFR2.3に基づく。 |
| 拡張範囲 | 追加会場・複数ベル・多人数イベントへの拡張は初版の性能目標に含めない。将来追加する場合、会場分離、ベル単位の権限・予定競合、トピック、負荷・費用を再評価する。 | Infrastructure Designで環境とキー設計が初版の1会場境界を越えて漏れないことを確認する。 |

アクセス頻度、会場数、同時主催者数の成長予測は与えられていない。過剰な高可用・水平分割構成を前提にしない。単一会場のイベント利用を超えるスケール保証や数値SLOは定義しない。
