# U1 セキュリティ要件

入力: [U1機能仕様](../functional-design/functional-spec.md)、[U1ルール](../functional-design/rules.md)、[requirements.md](../../../inception/requirements-analysis/requirements.md)、[contract-summary.md](../../../inception/contract-design/contract-summary.md)、[認証基盤の回答](nfr-requirements-questions.md)。

| ID | 要件 | 検証 |
|---|---|---|
| NFR3.1 | 公開APIは有効な認証トークンを検証し、venueIdから許可済み主催者のread/configure/operate権限を確認する。一般向け自己登録を提供せず、許可済み利用者のみを追加する。既存の認証基盤はないため、招待制マネージド認証を候補としてInfrastructure Designで選定する。 | 未認証、無効、期限切れ、許可外principalの直接APIアクセスを試し、401/403と状態不変を確認する。 |
| NFR3.2 | ブラウザーからAPI、およびバックエンドからAWSへの通信を暗号化する。HTTPで認証情報・秘密値を送信しない。 | TLS設定、無効証明書・HTTPアクセスの拒否を確認する。 |
| NFR3.3 | AWS資格情報・Pico証明書・認証秘密はリポジトリ、ブラウザー資産、API応答、ログに置かない。Pico用証明書はPico側だけに保持し、バックエンド用の秘密は実行時に保護された設定から読む。 | ソース・ビルド成果物・ログの秘密スキャンと権限確認を行う。 |
| NFR3.4 | バックエンド権限は必要なAPI、対象会場データ、対象IoTトピック、環境だけに限定する。dev/prodの送信先と認証情報を混在させない。 | 許可外トピック、会場、環境への操作を拒否する結合試験を行う。 |
| NFR3.5 | API入力はサーバー側で検証し、エラー・ログにトークン、秘密値、証明書、内部スタックを含めない。運用記録にはイベントタイマーに必要な識別子と結果のみを残す。 | 無効入力、認証失敗、例外経路の応答とログを検査する。 |
| NFR3.6 | 主催者は保存済みメール招待を使う前提とする。具体的な本人確認方法、招待担当、認証方式とトークン発行者はInfrastructure Designで確定する。 | 公開登録・無許可のアカウント作成経路がないことを確認する。 |

この初版では観客・登壇者の個人情報や支払い情報を収集しない。法規制認証や公開マルチテナント運用は対象外である。認証情報の具体的な保管サービスはAWS構成決定後に割り当てる。
