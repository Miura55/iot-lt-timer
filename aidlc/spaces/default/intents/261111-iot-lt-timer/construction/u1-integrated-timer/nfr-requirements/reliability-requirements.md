# U1 信頼性要件

入力: [U1機能仕様](../functional-design/functional-spec.md)、[U1ルール](../functional-design/rules.md)、[requirements.md](../../../inception/requirements-analysis/requirements.md)、[contract-summary.md](../../../inception/contract-design/contract-summary.md)。

| ID | 要件 | 検証 |
|---|---|---|
| NFR2.1 | 2xxで受理した開始・状態変更は耐久保存後にのみ成功として返し、RPO=0を目標とする。受理済みのsessionId、deadline、通知ID、結果はブラウザー切断や単一実行プロセスの再起動で失わない。 | 永続化直後に実行プロセスを停止・再起動し、同じdeadline・状態・通知結果を復元できるか確認する。 |
| NFR2.2 | 発表時間はサーバーUTC deadlineで進み、ブラウザーのスリープ・終了・時刻変更に依存しない。再接続後はサーバー状態を再取得する。 | ブラウザーを閉じて予定通知と完了を観察する。端末時刻を変更してもサーバー状態は変わらないことを確認する。 |
| NFR2.3 | 起床イベントは重複・早着・順不同・古い世代を許容し、各回で永続状態を再検査する。外部送信と保存の同時原子性は仮定せず、claim・lease・安定IDで回復する。 | 同じ起床を複数回発行、早期／古い世代を発行し、一つの有効な送信だけになることを確認する。 |
| NFR2.4 | 各TimerSessionにdeadline起床を登録し、通知0件でも期限時に完了処理を起こす。独立照合を60秒ごとに実行し、起床消失・登録失敗・期限切れleaseを検出する。正常起床時、通知0件はdeadlineで完了し、通知ありはdeadline経過かつ全通知終端で完了する。起床消失時の運用目標は、通知0件ならdeadline+65秒以内、通知ありならmax(deadline, 最新notification.expiresAt+65秒)以内に完了状態を永続化する。これはハードリアルタイム保証ではない。状態GETと新規開始でもdeadline後の論理完了を評価し、永続化済みの古いactive状態だけで新規開始を誤拒否しない。 | ブラウザーを閉じた通知0件の通常deadline起床・起床消失、予定通知の起床消失、登録失敗、lease切れを模擬する。各ケースで上記基準時刻からの終端確定と、旧session状態による誤った開始拒否がないことを確認する。 |
| NFR2.5 | 予定時刻から5秒以上経過した命令は再送しない。曖昧結果は期限内に同じcommandId・payloadで再試行する。いずれかの試行でAWS受付が確認できればsent、受付確認なしで曖昧さが残れば期限時にunknown、曖昧さがなく全試行の不受理が確定した場合だけfailedとする。AWSの受付はデバイス受信・鳴動保証でない。 | 曖昧後の受付、曖昧後の拒否、曖昧のまま期限、全拒否、未試行期限切れを模擬し、sent/unknown/failed/expiredの終端状態を確認する。 |
| NFR2.6 | ブラウザー通信断・認証切れ・AWS障害を成功表示に変えず、最終更新時刻、通知の不明・失敗・期限切れを文字で示す。内部dispatchingは公開APIでpendingに写像し、画面では「送信処理中」と示す。 | 401、403、429、503、ネットワーク切断、遅延応答を模擬する。内部dispatching中のGETがC1のpendingを返し、処理中表示となることも確認する。 |

数値の可用性SLAは設定しない。初版は単一リージョンでのイベント利用を対象とし、複数リージョン待機や常時運用の保証はしない。通知の送信期限を過ぎた障害では鳴動を追い付かせず、古い命令の再生防止を優先する。イベント前の実機検証と運用可否判断を必要とする。
