# LTタイマーの利用シナリオ

入力: [requirements.md](../requirements-analysis/requirements.md)、[team-practices.md](../practices-discovery/team-practices.md)、[質問回答](user-stories-questions.md)。利用者は[主催者P1](personas.md)。初版の範囲を増やさず、8件すべてMust Haveとする。

受け入れ条件のGiven/When/Thenは試験条件を表す。テスト実装の順番はtest-after。各シナリオは適切な状態を準備して単独で検証できる。依存は実装・操作の前提であり、他シナリオの試験の実行順には依存しない。認証・整合性・アクセシビリティは全画面の共通条件とする。

## US1.1 許可された主催者がログインする

主催者として、ログインして会場へアクセスしたい。第三者にベルを操作されずに準備・進行するためである。

- 優先度: Must Have。出典: FR1、NFR3。依存: なし。
- AC1.1.1 Given 許可済み主催者、When 有効な認証でアクセスする、Then 共有会場の設定と現在のタイマーを取得できる。
- AC1.1.2 Given 未認証または権限のない利用者、When 読取・操作APIへ直接アクセスする、Then 拒否され、状態と通知は変わらない。
- AC1.1.3 Given 認証の失敗、When 画面に結果を表示する、Then 再認証の方法を示し、資格情報・証明書を画面やログへ出さない。一般向けの自己登録を設けない。
- INVEST: 認証済み会場アクセスという独立した成果を検証可能。方式は設計で選べる。

## US1.2 時間とベル設定を保存して再利用する

主催者として、時間と残り時間ごとのベル回数を保存したい。同じ発表形式を手早く再利用するためである。

- 優先度: Must Have。出典: FR2、FR3、FR13、NFR4。依存: US1.1。
- AC1.2.1 Given 設定画面、When 時間1〜10800秒の整数と0〜10件のベルを保存する、Then 残り時間0〜設定時間、各1/2/3回の有効な設定を再読込して復元できる。残り0秒は終了時、残り設定時間と同値は開始直後を意味する。
- AC1.2.2 Given 無効な入力、When 0秒・負数・小数・10801秒・11件・時刻重複・範囲外時刻・回数0/4を送る、Then 画面とサーバーが拒否し、入力を保持して修正箇所を示す。
- AC1.2.3 Given 未保存または保存失敗、When 画面を表示する、Then 未保存と通信失敗を区別し、最後に保存成功した内容を失わない。実行中の設定変更は次回だけに適用する。
- AC1.2.4 Given PCまたは320 CSS px幅の画面、When キーボードで入力・保存する、Then 主要操作が欠けず、ラベルと文字の状態説明を利用できる。
- INVEST: 保存済み設定を成果とし、タイマーを開始せず単独確認可能。

## US1.3 開始し、ブラウザーを閉じても進行を確認する

主催者として、タイマーを開始して残り時間を確認したい。端末を開き続けなくても発表を進行するためである。

- 優先度: Must Have。出典: FR4、FR5、FR6、FR14、NFR2。依存: US1.1、US1.2。
- AC1.3.1 Given 有効な設定とタイマーなし、When 開始が受理される、Then バックエンドの識別子・状態・終了予定時刻を取得し、サーバー時刻を基準に残り時間を表示する。
- AC1.3.2 Given 実行中、When ブラウザーを閉じ再度開く、Then バックエンドは進行・通知を継続し、既存状態を復元できる。完了後は残り0秒を表示する。
- AC1.3.3 Given 二重送信または複数主催者の同時開始、When 開始を競合させる、Then 同時実行は1件だけで、拒否・再取得の必要を画面に示す。
- AC1.3.4 Given 状態取得が失敗、When 古い表示が残る、Then 更新失敗と最終更新を示し、新しい操作を成功扱いしない。古い応答で新しい表示を上書きしない。
- INVEST: バックエンド継続を含む縦の機能。設定・認証は試験用に準備可能。

## US1.4 一時停止する

主催者として、タイマーを一時停止したい。発表中断中に残り時間やベルが進まないようにするためである。

- 優先度: Must Have。出典: FR7、FR14、NFR2。依存: US1.3。
- AC1.4.1 Given 実行中、When 停止が受理される、Then 残り時間と未送信通知を保存し、停止中は新しい命令を送信しない。
- AC1.4.2 Given 停止APIの通信失敗、When 結果を表示する、Then 停止成功と表示せず、復旧後にサーバーの状態を再取得する。
- AC1.4.3 Given 通知と停止の競合、When 結果を確認する、Then サーバーで確定した順序に従い、既に送信した命令は取消不能であることを示す。古い状態からの操作は検出する。
- INVEST: 実行中状態を用意して単独検証可能。競合処理の実装方式は設計に委ねる。

## US1.5 残り時間を引き継いで再開する

主催者として、停止位置から再開したい。未実行のベル予定を保って発表を続けるためである。

- 優先度: Must Have。出典: FR8、FR14、NFR2。依存: US1.4。
- AC1.5.1 Given 停止中、When 再開が受理される、Then 保存した残り時間から新しい終了予定時刻を計算し、未送信通知を同じ残り時間で予定する。
- AC1.5.2 Given 既に送信済み通知がある、When 再開する、Then 同じ通知を再送しない。
- AC1.5.3 Given 実行中・取消済み・完了済みまたは古い状態、When 再開を要求する、Then 拒否と現在状態を表示する。再試行でも実行を重複させない。
- INVEST: 停止中の保存データを前提に独立試験可能。

## US1.6 キャンセルする

主催者として、発表タイマーを取り消したい。不要になったベル通知を止めるためである。

- 優先度: Must Have。出典: FR9、FR14、NFR2。依存: US1.3。
- AC1.6.1 Given 実行中または停止中、When キャンセルが受理される、Then 未送信通知を無効化して取消状態を表示する。
- AC1.6.2 Given 通知時刻直前、When 取消しと送信が競合する、Then 確定した順序に従い、既に送信した命令は取り消せないと表示する。
- AC1.6.3 Given 同じ取消しの再送または通信失敗、When 結果を確認する、Then 副作用は重複せず、未受理の操作を成功と表示しない。
- INVEST: 取消しの成果を実行中・停止中の各状態から単独確認可能。

## US1.7 ベル命令の送信結果を確認する

主催者として、通知が送信されたかを確認したい。通信障害を把握し、実際の鳴動と送信受付を混同しないためである。

- 優先度: Must Have。出典: FR10、FR11、FR12、NFR5。依存: US1.3。
- AC1.7.1 Given 有効な予定通知、When バックエンドがAWS IoT Coreへ命令を送る、Then 対象ベルへ1/2/3回を指示し、通知識別子・予定時刻・期限を含め、サービス受付を送信済みとして記録する。
- AC1.7.2 Given 予定、失敗、期限切れ、取消し、結果不明の各通知、When 結果を表示する、Then それぞれを文字で区別し、結果不明を成功に変えない。Picoの接続状態や実行成功は表示しない。
- AC1.7.3 Given 予定から5秒以上経過した未送信命令、When 送信処理が再開する、Then 送らず期限切れを記録する。デバイス契約も期限切れ・重複識別子の実行を防ぐ。
- AC1.7.4 Given 障害調査、When 操作・実行・通知の記録を確認する、Then 識別子で追跡でき、秘密情報がなく、提案の7日保持後に運用履歴を削除する。
- INVEST: 通知処理と表示を一つの観測可能な成果として検証可能。デバイス返信は不要。

## US1.8 イベント前に接続と時刻精度を確認する

主催者として、模擬受信と実機で接続を確認したい。11月14日のイベントで利用できるか判断するためである。

- 優先度: Must Have。出典: FR15、NFR1、NFR3、NFR6、開発方針。依存: US1.3、US1.7。
- AC1.8.1 Given アプリ側仕様と模擬受信環境、When 通知を送る、Then トピック・ペイロード・期限・回数・重複排除の仕様と一致することを確認できる。Picoのファームウェア自体は依頼者が実装する。
- AC1.8.2 Given 実機と正常接続、When 各1/2/3回を10件ずつ計30通知で試験する、Then 最初の打音の遅れ・欠落・重複を観察記録し、全30件2秒以内を目標達成と判定する。未達・未実施は成功にせず利用可否を依頼者が判断する。
- AC1.8.3 Given 期限切れ・重複命令、When 実機で受信する、Then 古い命令や重複識別子で鳴らさないことを観察確認する。実機からの返信を追加しない。
- AC1.8.4 Given 機構の打音間隔と3回鳴動所要時間が未確定、When イベント用の設定を準備する、Then 近接通知の安全性を確認済みと扱わない。実機仕様で最小間隔・競合時の順序・2秒目標の適用を確定するまでは十分離した通知だけを使い、具体的な間隔は接続検証計画で決める。
- AC1.8.5 Given 統合前の変更、When CIを実行する、Then test-afterで用意した単体・主要境界の結合テスト、行カバレッジ80%以上、整形・静的解析の成功を確認する。
- INVEST: 利用可否の判定が成果。模擬と実機の証拠を分け、実機準備を依頼者依存として明示する。

## 共通の境界と後続設計

- 送信受付は鳴動保証ではない。バックエンド管理でも通信遅延・物理動作の遅れは残る。
- ログイン方式、時間管理方式、操作と送信の直列化、打音間隔、費用試算は後続設計で確定する。
- NFRは下記対応表でシナリオへ追跡し、詳細な検証環境・実装方式はnfr-requirements / nfr-designで具体化する。
- 観客画面、進行表、デバイスACK、複数会場は対象外。月額500円目安と東京リージョン、11月14日目標を維持する。
