# 順序の理由とリスク

入力: [requirements.md](../requirements-analysis/requirements.md)、[stories.md](../user-stories/stories.md)、[components.md](../domain-design/components.md)、[unit-of-work.md](../units-generation/unit-of-work.md)、[unit-of-work-dependency.md](../units-generation/unit-of-work-dependency.md)、[contract-summary.md](../contract-design/contract-summary.md)、[回答](delivery-planning-questions.md)。

依頼者は点数方式ではなく、イベント利用に必要な依存順とリスクで順序を決めると回答した。最初に全体をつなぐ最小構成を確認し、Unit単位で直列に進める。Unit DAGはU1 → U2 → U3であるため、経済的な再順位付けは行わない。U1は最初の一連動作を通す歩く骨格であり、後続Unitを先に実装しても価値が出ない。

## リスク一覧

| リスク | 起こりやすさ | 影響 | 対応と順序への反映 |
|---|---|---|---|
| Pico側受信実装・機構の準備が遅れる、または受信契約に不一致がある | 中 | 高 | 依頼者の見込みは11月13日まで。U1で模擬受信を先に作り、トピック・期限・重複排除・0.5秒間隔を早期に突合する。遅れたら模擬試験とアプリ開発を続け、実機未確認のままイベント利用可とは判定しない。 |
| 残り時間の予定が遅れる、またはAWS IoT送信受付が実鳴動と誤認される | 中 | 高 | U1でバックエンドの時刻管理、期限付き命令、送信結果の区別を通しで確認する。実機試験は30通知で測り、送信受付を実鳴動成功と表示しない。 |
| 機構の復帰時間が2秒の予定最小間隔に足りない | 中 | 高 | 実機で各打音後の復帰時間と欠落を記録する。必要ならベル設定の最小通知間隔を拡大し、API検証・保存設定・試験条件を揃えて更新する。 |
| 同時操作、再試行、停止・取消しと送信が競合する | 中 | 高 | U1で開始の冪等性・期限確認、U2で状態版・世代・送信境界・未知結果の回復を実装し、競合を結合試験する。AWS送信と永続化の原子性は仮定しない。 |
| 11月14日の利用目標までにAWS環境や認証方式が決まらない | 中 | 高 | Infrastructure Designで東京リージョン、認証、開発／本番分離、権限、試算を先に決める。接続情報が整う前は模擬環境を進め、実AWS接続を完了扱いしない。月額500円は目安であり自動停止の上限ではない。 |
| イベント前に実ベル30通知を測定できない、または目標超過が残る | 中 | 高 | 準備でき次第、実機を早期に接続して検証する。未実施や超過を隠さず記録し、イベント使用は依頼者が判断する。 |

## 順序のトレードオフ

全機能を一つの大きなUnitにまとめる案は、中間で接続障害や時間誤差を見つけにくいため採用しない。コンポーネントごとの水平分割はU1だけで画面からベルまで確認できず、希望する最初の成果に合わないため採用しない。Unitごとに直列で実装し、各段階に具体的な動作デモを置くことで、期限と不確実性への対応を優先する。
