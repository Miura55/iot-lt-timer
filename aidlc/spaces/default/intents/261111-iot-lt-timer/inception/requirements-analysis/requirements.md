# IoT LTタイマーの要件

## 意図と利用範囲

LTの主催者が時間経過に合わせて自作ベルを鳴らし、ブラウザーやデバイスの時計への依存を抑えて発表を進行する。初版はログインした少人数の主催者、1会場、ベル1台、同時タイマー1件。利用目標日は2026年11月14日のイベント。

## Sources

- 初期依頼（project-description.json）: 「IoT化したベルと連動したLTタイマーのアプリを開発したいです」。
- 会話での追加条件: AWS IoT Core MQTT、依頼者実装のRaspberry Pi Pico、ブラウザーで任意時間・各1/2/3回のベル設定、複数の通知時刻、バックエンドでの時間管理、一時停止・再開・キャンセル。
- [requirements-analysis-questions.md](requirements-analysis-questions.md) Q1〜Q8: 利用範囲、残り時間指定、入力範囲、精度目標、停止操作、画面、予算・期限、送信までの責任範囲。
- [team-practices.md](../practices-discovery/team-practices.md): mainへのsquash統合、最小構成での接続確認、test-after、行カバレッジ80%以上、CI、公開方針。

## 機能要件

以下はすべて初版のMust。設定保存は初版に含むが、イベント進行表は含めない。

| ID | 要件と出典 | 受け入れ条件（正常・境界・失敗） |
|---|---|---|
| FR1 | 主催者の認証・操作制限（Q1） | 未認証での読取・操作を拒否する。認証済みの許可された主催者だけが共有会場を操作できる。登録を一般公開しない。認証方式は設計で決定する。 |
| FR2 | タイマー時間設定（Q3） | 1〜10800秒の整数を受け付ける。0、負数、小数、空欄、10801秒を拒否し、入力を保持して修正箇所を示す。サーバーでも同じ検証をする。 |
| FR3 | 複数のベル時刻と回数（会話・Q2/Q3） | 残り時間0〜設定時間の範囲で最大10件を設定でき、各回数は1/2/3のみ。残り0秒は終了時。開始時点と同じ残り時間は開始直後の通知になる。重複時刻、範囲外、11件、回数0/4を拒否する。 |
| FR4 | タイマー開始（Q1/Q5） | 有効な設定で開始するとバックエンドが識別子・終了予定時刻・状態を確定する。タイマーなしからの開始は1件だけ成功し、二重送信や同時開始で複数の実行を作らない。受理されなかった操作はエラーとして表示する。 |
| FR5 | バックエンドの時間管理（会話） | ブラウザーを閉じてもタイマーと未実行通知が継続する。実行中のベル予定時刻をバックエンドが保持し、Picoは受け取った命令を実行する。ブラウザーやPicoにタイマー全体の時間管理を委ねない。 |
| FR6 | 残り時間と状態の表示（Q6） | ブラウザーはサーバーが返す時刻・状態を基準に表示する。再読込で既存タイマーを復元する。通信失敗時は表示の更新失敗・最終更新を示し、古い状態を最新と表示しない。完了後の残り時間は0で固定する。 |
| FR7 | 一時停止（Q5） | 実行中に停止が受理されると、残り時間と未送信通知を保存する。停止中は新しいベル命令を送信しない。既に送信した命令の取消しは保証しない。操作完了の表示はサーバー受理後とする。 |
| FR8 | 再開（Q5） | 停止中に再開すると保存した残り時間から再開し、未送信通知の時刻を再計算する。既に送った通知は再送しない。不正な状態からの再開は拒否する。 |
| FR9 | キャンセル（Q5） | 実行中・停止中のキャンセル受理後は未送信の通知を無効にする。終了直前の競合でも受理結果に応じた状態を表示する。既に送信した命令は取り消せないと操作画面で説明する。 |
| FR10 | AWS IoT CoreへのMQTT命令送信（会話・Q8） | 各通知で対象ベルに予定した1/2/3回の命令を送信する。送信結果をサーバー側に記録し、サービスによる受付を送信済みとする。ベルの受信・鳴動成功とは区別する。 |
| FR11 | 遅延・重複に対応する命令仕様（Q4） | 命令は通知識別子、予定時刻、有効期限、回数を持つ。予定時刻から5秒以上経過した未送信命令を送らない。再接続時に期限切れ命令を鳴らさないことと、同じ識別子の重複実行を防ぐことをPico側の契約に明記する。 |
| FR12 | 通知結果・失敗表示（Q4/Q6/Q8） | 予定、送信済み、送信失敗、期限切れ、取消しを区別する。送信結果不明は不明と表示し、成功に置き換えない。デバイスの接続状態・受信結果・実行結果は取得も表示もしない。 |
| FR13 | 設定の保存・再利用（Q6） | 会場の時間・ベル設定を保存して再読込・次回開始に再利用できる。初期状態は設定未保存と表示する。保存失敗を通知し、最後に保存成功した内容を失わない。実行中の設定変更は現在の実行に反映せず、次回開始から適用する。 |
| FR14 | 同時操作の整合性（Q1/Q5） | 複数タブ・主催者の競合をサーバーで検出する。古い状態での操作を拒否し再取得を促す。同じ操作識別子での再試行は副作用を重複させない。停止・再開・取消しと通知送信の競合ルールを設計で明記する。 |
| FR15 | MQTT仕様と接続検証手順（Q8・開発方針） | アプリが送るトピック・ペイロード・期限・重複排除・回数の意味を文書化し、模擬受信で検証できる。実機確認では返信を追加せず、目視・録画等で回数と遅れを確認する。 |

## 制約と期限

- AWSリージョンは東京。AWS IoT Core MQTTを利用する。
- バックエンド管理の方式はStep Functions等を比較して設計で決める。先の会話のAPI Gateway/Lambda構成は案であり確定ではない。
- Raspberry Pi Picoによるベルのファームウェア・機構は依頼者が用意する。MQTT命令の受信・期限検査・重複排除は連携契約として依頼する。返信は初版では不要。
- 月額500円を目安とする。依頼者の原文: 「500円（クレジットがあるので特に気にしない）」。クレジット適用前の費用と、利用条件を明記した試算を設計で提示する。超過時の自動課金停止は要件に含めない。
- 2026年11月14日イベントでの利用を目標とする。具体的なイベント開始時刻・実機準備状況は接続検証計画までに確認する。完成・利用可否は実機確認結果に依存する。

## 仮定と判断理由

- 端末・バックエンド・ネットワークはベストエフォートであり、時計の統一はネットワーク遅延や物理動作を消さない。測定目標と送信確認の境界を分ける。
- 通知0件のタイマーも表示用途として許可する。1〜10件という下限指定は依頼されていないため、通知リストの空をエラーにしない。
- 7日の運用履歴保持はトラブル調査と低費用のための提案。会場の設定は削除または上書きまで保持する。登壇者・観客の個人情報は収集しない。
- 初版は1会場の共有設定であり、主催者別の独立データや一般利用者の自己登録を含めない。
- 通信不能時のブラウザーは新規操作を成功扱いせず、復旧後にサーバー状態を再取得する。バックエンドが動作していればベル送信は継続する。

## 対象外

- Picoのファームウェア・ベル機構そのものの開発、デバイスのオンライン表示、受信・実行ACK、自動的な実鳴動の成功判定。
- 複数会場・複数ベルへの拡張、観客専用画面、登壇者管理、イベント進行表、連続自動進行、ブラウザー音の代替ベル。
- 履歴の検索・ページング・エクスポート、課金管理画面、一般公開向けテナント管理、多言語対応。
- 通信断でも定刻に鳴る保証、サブ秒の精度保証、送信済み命令の取消し。

## 後続で確定する事項

- 接続検証計画: イベント時刻、実機準備日、試験場所のネットワーク条件。未実施の実機検証は完了と記録しない。
